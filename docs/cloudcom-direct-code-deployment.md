# CloudCom direct production code workflow

**Current owner decision (2026-09-25):** Ordinary Cloud Command extension fixes are edited in the single `C:\Users\AGUILERA\Codex\cloudcom-dev` checkout, checked locally, then copied directly into the editable `/opt/cloudcom/live-code` tree on Lightsail. API and Exchange worker mount that tree read-only inside their containers. Back up the touched file, replace it atomically, restart only its affected service, and verify health and the live UI. Do not require a versioned artifact, signature, GitHub Action, GIT VM, branch, worktree, or Docker image for these changes. Keep the GIT VM off until a LanternOps intake. The live service remains reachable if the GIT VM is off.

The existing image digests stay fixed between LanternOps intakes. Runtime dependency or schema changes require explicit compatibility and database-backup review; the owner has not waived those technical constraints. Native Windows agent/MSI and RustDesk binaries still require a build and update path, separate from ordinary extension edits. `/opt/cloudcom/deployment/compose.before-direct-code-20260925T213527Z.json` is the pre-transition Compose rollback point. `/opt/cloudcom/live-code.rollback` is the one retained runtime backup for the direct-code update. The older signed-artifact process described below is historical, not a prerequisite for ordinary extension work.

CloudCom uses one persistent source checkout for ordinary development. Edit and run focused tests there without creating a branch, candidate image, or public version for every iteration. Git records an exact source checkpoint when integrating a LanternOps release or publishing a distributable release.

## When images are allowed

Build new CloudCom runtime images only for the commit that advances `.github/cloudcom-baseline.json` to a published LanternOps release. `cloudcom-candidate.yml` enforces this with `require-upstream-intake.mjs`, in addition to its exact-main-commit and successful-CI requirements. A routine CloudCom feature commit must not use the candidate-image workflow. Windows agent/MSI and RustDesk client packages are separate deliverables, not Docker images.

An upstream intake still requires a database/configuration backup, published-tag provenance, review of migrations and CloudCom attachments, tests, signed release inventory, and a health-checked deployment. No upstream image is substituted for a CloudCom image: PAM, remote access, and Extensions must be present in the combined source. Keep the running image and a tested rollback image per component; remove older unused candidates only after checking container references and recovery artifacts. Never prune application data volumes to reclaim image space.

## Ordinary CloudCom releases without new images

The desired path is a frozen source revision built on the existing test runner into versioned application artifacts, with a signed manifest containing each archive hash, source commit, upstream-runtime image digests, and expected database migration set. The production host verifies that manifest before unpacking into a new release directory. A read-only Compose override mounts the API, web, portal, and extension runtime artifacts over the compatible intake images; the affected containers are recreated with the **same** image digests. Keep the prior artifact directory and override for rollback. Do not edit files inside a running container or replace a live release directory in place.

Dependency and runtime compatibility are a hard gate: a feature release may use this path only when its runtime dependencies and image contract still match the intake images. Otherwise defer that feature to the next LanternOps intake, or obtain an explicit change to this rule. Before any schema migration, take and verify a database backup; an application rollback alone does not reverse migrations. Native agent releases retain their own MSI, version, manifest, and acceptance process.

**Current implementation status (2026-09-25):** an initial no-image path is implemented and live for compatible API, Cloud Command browser bundle, and Exchange worker script changes. `scripts/release/feature-artifact.mjs` signs exact file hashes and binds both running image digests to the upstream source commit; `feature_compose.py` creates read-only mounts, and `promote-feature-artifact.sh` keeps a Compose backup and restores both services on failed health checks. This path passed a disposable GIT stack test and a deliberately broken-bundle rollback test before Lightsail promotion. A local, **not yet production-tested**, schema-v3 extension adds signed Cloud Command manifest/SQL files as read-only mounts. It passed GIT artifact checks, a disposable PostgreSQL migration and backup/restore drill, and a disposable signed API/worker promotion with an intentionally unhealthy signed artifact that triggered Compose/service rollback; the disposable stack was removed afterward. The production trust copies of `feature-artifact.mjs`, `feature_compose.py`, and the promoter must be updated and verified together before a schema-v3 artifact can be accepted; keep the existing Ed25519 trust key unchanged. Promotion of schema-v3 requires an operator-created database backup under `/opt/cloudcom/deployment/backups` and its matching SHA-256 via `CLOUDCOM_FEATURE_DB_BACKUP` and `CLOUDCOM_FEATURE_DB_BACKUP_SHA256`; the hash check verifies the backup file's identity, while a separate restore drill is still required to prove recoverability. Application rollback does not undo applied DDL. Every later feature artifact must carry all post-intake Cloud Command migration mounts, or promotion rejects their removal. The core web or portal bundles, native agents, and dependency changes still require their own release procedures. Keep the release artifact and prior Compose backup for rollback.

The next intended CloudCom agent version is `0.116.4`, advancing the existing Windows `0.115.4` release. Record the exact upstream tag and CloudCom source commit separately in each release manifest; the agent version alone is not source provenance. Build and verify each platform's agent, sidecars, installer or package, and update manifest from its frozen source before promoting that platform. A server upgrade to v0.116.0 does not by itself update any endpoint. Do not mark the fleet at `0.116.4` until endpoint heartbeats confirm it, and do not publish an `0.116.4` asset for a platform that has not passed its package and update tests.
